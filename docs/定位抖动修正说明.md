# 定位抖动修正说明

本文只说明一个核心问题：相对于旧版本 `bf36e9f203cef6b26c048852c93d451d9c4e6a77`，为什么将网络结构从 `mobilenetv3 + FPN` 收敛到 `ResNet18 + 专用 decoder` 后，定位抖动明显减小。

## 1. 结论

这次“修抖动”的核心，不是额外加了滤波器，而是让模型本身输出更稳定的中心峰值。

旧版本的默认结构是：

- `mobilenetv3_large` backbone
- `FPNFusion` neck
- `CenterNetHead`

当前版本的结构是：

- `ResNet18Backbone`
- `ResNetCenterNetDecoder`
- `CenterNetHead`

对应代码变化：

- 旧版模型组装在 `src/centernet_spot/model.py` 中通过 `build_backbone()` 和 `FPNFusion` 组合。
- 当前版本在 [src/centernet_spot/model.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/model.py) 中固定使用 `ResNet18Backbone + ResNetCenterNetDecoder`。
- 旧版通用 FPN 实现在旧版 `src/centernet_spot/neck.py` 中。
- 当前版本专用 decoder 实现在 [src/centernet_spot/neck.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/neck.py) 中。

可以把这次变化概括成一句话：

> 从“面向通用性的轻量多尺度融合结构”，收敛到“面向当前光斑定位任务的稳定型中心点解码结构”。

## 2. 旧结构是什么

旧版本 `bf36e9f...` 的默认路径可以概括为：

```text
输入图像
  -> MobileNetV3-Large
  -> 多层特征图
  -> FPNFusion
  -> heatmap / reg head
```

旧版 [model.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/model.py) 的关键逻辑是：

- backbone 通过配置动态选择
- 默认配置里 backbone 是 `mobilenetv3_large`
- neck 使用统一的 `FPNFusion`

旧版 `FPNFusion` 的做法是：

1. 先把不同尺度特征都投影到统一通道数。
2. 从最深层特征开始逐层上采样。
3. 每一层把“当前层 lateral 特征”和“上一层上采样结果”拼接后再 refine。
4. 最后得到用于 CenterNet head 的融合特征。

这种结构的优点是：

- 通用
- 容易适配多种 backbone
- 计算量相对可控

但它也有一个天然代价：它优先优化的是“多尺度信息融合”，不是“单个中心点峰值位置的稳定性”。

## 3. 为什么旧结构更容易抖

对于当前任务，最终输出不是分类框，而是一个中心点 `(x, y)`。所以真正重要的不是“能不能大概看见目标”，而是：

- 热力图峰值能不能持续落在同一小片区域
- 峰值附近的响应面是不是够尖锐、够稳定
- 回归偏移 `reg` 在相邻帧是不是会小幅乱摆

旧结构在这件事上有几个不利因素。

### 3.1 MobileNetV3 更偏轻量表达，局部峰值稳定性不足

`mobilenetv3_large` 的设计目标首先是效率，不是极致的定位稳定性。它大量使用：

- depthwise separable convolution
- 轻量瓶颈结构
- 更强的通道压缩

这些设计对于分类和一般检测通常没问题，但在当前这种“要从热力图里读一个非常稳定的点”的任务里，容易出现一个现象：

- 模型能检测到光斑
- 但热力图最高点在相邻像素之间轻微漂移

这种漂移在静态图片里不明显，在视频里就会变成坐标抖动。

原因不在于 MobileNetV3 “不能用”，而在于它更偏向轻量表达，特征冗余更少。对于亮斑这种局部结构简单、但位置精度要求很高的目标，轻量 backbone 对亮度波动、边缘模糊、噪声扰动的容忍度通常不如更厚实的 ResNet 特征。

### 3.2 统一 FPN 融合会引入额外的位置扰动

旧版 `FPNFusion` 有一个关键路径：

```text
深层特征
  -> 上采样
  -> 与浅层 lateral 特征拼接
  -> refine
  -> 再上采样
  -> 再拼接
```

这个路径的问题不是“错误”，而是对点定位任务来说，它可能让峰值中心更容易摆动。

原因有三点。

第一，多次插值上采样本身会改变局部响应分布。

对于框检测，这种变化通常问题不大；但对于中心点热力图，一个峰值如果本来只差半个像素，多次上采样后局部最大值所在位置就更容易在相邻格点间切换。

第二，浅层与深层特征拼接后，响应中心可能被重新分配。

浅层特征保留更多边缘和纹理，深层特征保留更多语义。对一般检测，这是好事；但对当前亮斑定位，浅层纹理噪声、反光边缘、局部亮度起伏也可能被重新混进最终特征，使热力图峰值在“亮斑中心”和“亮斑局部高响应边缘”之间反复竞争。

第三，统一 FPN 是为“多 backbone 通用”设计的，不是为当前 backbone 单独调的。

这意味着它的 lateral 通道、refine 方式、融合路径，更多是在兼容性和通用性上折中，而不是围绕当前任务去压峰值摆动。

### 3.3 多 backbone 通用设计带来了额外结构妥协

旧版代码允许：

- `dla34`
- `resnet18`
- `mobilenetv3_large`

共用一套组装逻辑。

这种设计的好处是试验方便，但代价是 neck/head 往往不能对某一个 backbone 做非常强的定制优化。结果就是：

- 为了适配多种输出通道和特征风格，结构要足够通用
- 一旦结构足够通用，就很难把“当前任务里最稳定的响应路径”压缩到最短

对光斑中心点这种任务，路径越绕、融合越多、插值越多，最终峰值位置就越容易抖。

## 4. 新结构改成了什么

当前版本把模型收敛成一条固定路径：

```text
输入图像
  -> ResNet18Backbone
  -> 最深层特征
  -> 3-stage conv + deconv decoder
  -> heatmap / reg head
```

当前 [model.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/model.py) 的核心变化是：

- 不再动态构造 backbone
- 直接固定为 `ResNet18Backbone`
- 不再使用 `FPNFusion`
- 直接使用 `ResNetCenterNetDecoder`

当前 [neck.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/neck.py) 的 decoder 逻辑很直接：

1. 取 `ResNet18` 最深层特征 `features[-1]`
2. 连续做三段：
   - `3x3 Conv + BN + ReLU`
   - `ConvTranspose2d stride=2`
3. 逐步恢复到检测头所需分辨率

这条路径比旧版 FPN 明显更短、更直接。

## 5. 为什么 `ResNet18 + 专用 decoder` 更稳

### 5.1 ResNet18 的特征更“厚”，对亮斑中心更稳

`ResNet18` 虽然不算很大，但比 `mobilenetv3_large` 更偏传统卷积骨干，特征表达的冗余度更高，残差结构也更稳定。

对当前任务，这通常带来两个好处：

1. 对局部亮度变化不那么敏感。
2. 对中心点附近的响应更连续，不容易一帧偏左一帧偏右。

从任务本质上说，光斑定位并不需要复杂语义类别区分，而需要：

- 对“亮斑整体中心”形成稳定表征
- 不要被局部最亮边缘牵着走

`ResNet18` 在这种“稳定地提取中心结构”上，比轻量 backbone 更合适。

### 5.2 专用 decoder 减少了多尺度融合带来的峰值竞争

新 decoder 不再把多层特征反复 lateral、拼接、refine，而是直接从最深层特征一路上采样回来。

这有一个非常关键的效果：

- 最终 heatmap 的峰值更主要由深层稳定语义控制
- 不会在多个尺度特征之间反复做“谁更像中心点”的竞争

旧版 FPN 的问题不是没有信息，而是信息太杂。对于亮斑中心定位，太多浅层纹理信息并不一定是帮助，反而可能让响应中心偏向局部高亮边缘、噪声点或反光轮廓。

现在改成专用 decoder 后，信号路径更单纯：

- 先在高层特征里确定“中心大概在哪”
- 再通过反卷积把这个中心位置稳定地恢复到输出分辨率

对“减少抖动”来说，这比“把所有尺度都混起来再判断一次”更有效。

### 5.3 三段固定反卷积路径让坐标恢复更可控

当前 decoder 的三段结构是固定的：

- `512 -> 256 -> upsample`
- `256 -> 128 -> upsample`
- `128 -> 64 -> upsample`

并且转置卷积初始化使用了接近双线性上采样的权重。

这类设计的好处是：

- 上采样行为稳定
- 输出空间的恢复路径固定
- 不依赖 FPN 多支路在不同层之间反复对齐

对于 CenterNet 这类中心点检测，输出热力图的空间一致性非常重要。当前 decoder 等于是在用一条单路径、低分叉的方式恢复空间分辨率，这会降低峰值中心在局部区域里的漂移概率。

### 5.4 “专门为 ResNet18 写 decoder”本身就是稳定性优化

当前版本不是简单把 backbone 换成 `ResNet18`，而是连同 neck 一起专门收敛了。

这点很关键。

如果只是把旧 FPN 挂到 `ResNet18` 上，效果未必会这么明显。真正带来稳定性的，是这两个动作一起发生：

1. backbone 固定为 `ResNet18`
2. decoder 专门围绕 `ResNet18` 的最深层特征来设计

这样做之后，模型不再需要兼容多种 backbone 输出风格，整个检测主干就只服务一件事：

- 稳定地产生单峰值、易解码的 heatmap

从工程角度看，这等于把“通用结构”改成了“任务专用结构”，而定位抖动正是这种任务专用优化最容易直接受益的问题。

## 6. 从输出行为上怎么理解“为什么更稳”

把两种结构的输出行为做一个直观对比：

旧结构更像是：

```text
多个尺度都来参与判断中心点
-> 信息更丰富
-> 但峰值中心更容易在局部区域内竞争和摆动
```

新结构更像是：

```text
先由深层特征确定中心
-> 再沿一条固定路径恢复分辨率
-> 峰值位置更集中、更连续
```

对于视频中的光斑，这种差异会表现为：

- 旧结构：帧与帧之间点能跟上，但坐标在附近来回小跳
- 新结构：点仍然能跟上，但中心位置更“钉住”真实光斑

这就是当前版本里“抖动被修正”的核心来源。

## 7. 代码层面的关键变化总结

### 7.1 旧版

旧版 `src/centernet_spot/model.py`：

- `build_backbone(backbone_name, **backbone_kwargs)`
- `self.neck = FPNFusion(fpn_in_channels, neck_channels)`

说明旧版是：

- backbone 可配置
- neck 是统一 FPN

### 7.2 当前版

当前 [src/centernet_spot/model.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/model.py)：

- `self.backbone = ResNet18Backbone(...)`
- `self.decoder = ResNetCenterNetDecoder(...)`

当前 [src/centernet_spot/neck.py](/Users/lexiangrui/Desktop/光斑定位-centernet/src/centernet_spot/neck.py)：

- 只保留 `ResNetCenterNetDecoder`
- 直接对 `features[-1]` 做三段卷积 + 反卷积恢复

这说明当前代码已经明确放弃“多 backbone 共用一套 neck”的思路，而是直接为当前任务锁定最稳的一条结构路径。

## 8. 总结

如果只看这次修抖动里“网络结构”这一条主线，核心逻辑是：

1. 旧版 `mobilenetv3 + FPN` 更偏轻量和通用，适合快速试验，但对点目标中心的单峰稳定性不够强。
2. `FPN` 的多尺度插值、拼接、refine 会让热力图峰值更容易受局部纹理和多层响应竞争影响。
3. 当前版本改成 `ResNet18 + 专用 decoder` 后，特征表达更稳、解码路径更短、空间恢复更直接。
4. 最终结果就是：同一真实光斑在相邻帧中的热力图峰值更连续，回归偏移更稳定，坐标抖动更小。

所以，从模型角度看，这次修正的本质不是“做平滑”，而是：

> 通过更稳的 backbone 和更直接的专用 decoder，让中心点本身不再乱跳。
